## Задание 1. Компилирование, исполняемый файл

### 1.1 Удаление временных файлов

Перед началом работы были удалены папки `bin` и `obj`, которые хранят артефакты сборки проекта. Удаление выполнено через терминал PowerShell командами:

```powershell
Remove-Item -Recurse -Force bin
Remove-Item -Recurse -Force obj
```

- `-Recurse` — удаляет папку вместе со всем её содержимым (подпапками и файлами).
- `-Force` — принудительное удаление, без дополнительных подтверждений.

### 1.2 Попытка запуска без компиляции

Была выполнена команда:

```powershell
dotnet run --no-build
```

**Результат — программа не запустилась, возникла ошибка:**

```
Unhandled exception: An error occurred trying to start process
'C:\...\lab2\bin\Debug\net10.0\lab2.exe' with working directory '...'.
Не удается найти указанный файл.
```

**Наблюдения и объяснение:**

Исходный код программы (файл `Program.cs`) нельзя запустить напрямую — компьютер понимает только машинный код, а не текст на языке C#. Чтобы программа заработала, исходный код должен пройти этап **компиляции** — преобразования текста программы в исполняемый файл (`.exe`).

Обычно команда `dotnet run` сама автоматически компилирует проект перед запуском. Но флаг `--no-build` специально отключает этот шаг компиляции и заставляет dotnet сразу искать уже готовый exe-файл. Так как папка `bin` (где хранится exe-файл) была предварительно удалена, dotnet не смог найти файл для запуска — отсюда и ошибка «Не удается найти указанный файл».

**Вывод:** выполнимый файл — это результат компиляции, а не сам исходный код. Без предварительной компиляции запускать нечего.

### 1.3 Воссоздание исполняемого файла

Для повторной сборки проекта использована команда:

```powershell
dotnet build
```

**Результат выполнения:**

```
Восстановление завершено (1,4 с)
  lab2 net10.0 успешно выполнено (1,6 с) → bin\Debug\net10.0\lab2.dll

Сборка успешно выполнена через 4,7 с
```

После выполнения команды папки `bin` и `obj` были созданы заново:

- **`obj`** — содержит промежуточные файлы, которые компилятор использует в процессе сборки (временные данные, не являющиеся конечным результатом).
- **`bin`** — содержит итоговые артефакты компиляции, включая готовый исполняемый файл (`lab2.exe`) и библиотеку (`lab2.dll`).

### 1.4 Поиск и запуск исполняемого файла

Исполняемый файл был найден по пути:

```
lab2\bin\Debug\net10.0\lab2.exe
```

(название папки `net10.0` соответствует установленной версии .NET)

**Первая попытка запуска (двойным кликом через Проводник Windows):**

Окно консоли открылось и **сразу же закрылось**. Программа выполнилась мгновенно (напечатала текст в консоль) и сразу завершила работу — операционная система автоматически закрывает окно консоли сразу после завершения процесса.

**Решение проблемы:**

Чтобы окно консоли оставалось открытым и не закрывалось само, в конец файла `Program.cs` была добавлена инструкция ожидания ввода:

```csharp
Console.WriteLine("Hello, World!");
Console.ReadKey(); // ждёт нажатия любой клавиши пользователем
```

`Console.ReadKey()` — это инструкция, которая приостанавливает выполнение программы и ждёт, пока пользователь не нажмёт любую клавишу на клавиатуре. Только после этого действия программа завершается, и окно консоли закрывается.

После добавления этой строки проект был пересобран командой `dotnet build`, и при повторном запуске `lab2.exe` окно консоли корректно оставалось открытым до нажатия клавиши.

**Запуск через терминал (альтернативный способ):**

Помимо запуска двойным кликом, исполняемый файл был также запущен через командную строку:

```powershell
cd bin/Debug/net10.0
.\lab2.exe
```

Оба способа запуска (через Проводник Windows и через терминал) дали одинаковый результат — программа корректно выполнилась.

**Важное замечание:** при попытке пересобрать проект (`dotnet build`), пока запущенный `lab2.exe` ещё «висел» открытым (ожидая нажатия клавиши через `Console.ReadKey()`), возникла ошибка:

```
error MSB3021: не удалось скопировать файл "...apphost.exe" в "...lab2.exe".
The process cannot access the file '...\lab2.exe' because it is being
used by another process.
```

**Объяснение:** пока exe-файл запущен (процесс работает и ждёт нажатия клавиши), операционная система блокирует его от изменений — компилятор не может перезаписать файл, который используется другим процессом. Решение — закрыть все открытые окна с запущенной программой перед повторной сборкой.

## Задание 2. Базовые инструкции

### 2.1 Вывод текста "Hello, Jerry"

**Код:**

```csharp
Console.WriteLine("Hello, Jerry");
Console.ReadKey();
```

**Результат в консоли:**

```
Hello, Jerry
```

`Console.WriteLine()` — инструкция, которая печатает переданный ей текст в консоль и переводит курсор на новую строку.

### 2.2 Функция с многократным вызовом и задержкой

**Код:**

```csharp
PrintABC();
Thread.Sleep(500);
PrintABC();
Thread.Sleep(500);
PrintABC();

Console.ReadKey();

void PrintABC()
{
    Console.WriteLine("A");
    Console.WriteLine("B");
    Console.WriteLine("C");
}
```

**Результат в консоли:**

```
A
B
C
A
B
C
A
B
C
```

**Пояснения:**

- `void PrintABC()` — определение функции без возвращаемого значения (`void`), которая последовательно печатает буквы A, B и C.
- `PrintABC();` — вызов функции. Каждый вызов запускает выполнение всех инструкций внутри тела функции.
- `Thread.Sleep(500)` — инструкция, приостанавливающая выполнение программы на 500 миллисекунд (0.5 секунды) перед выполнением следующей инструкции. Число передаётся в миллисекундах, поэтому 0.5 секунды = 500 мс.

Функция была вызвана 3 раза подряд, с задержкой в 0.5 секунды между вторым и первым, а также между третьим и вторым вызовами.

### 2.3 Три функции, вызывающие друг друга

**Код:**

```csharp
A();
A();
A();

Console.ReadKey();

void A()
{
    Console.WriteLine("Это функция A");
    B();
    C();
}

void B()
{
    Console.WriteLine("Это функция B");
}

void C()
{
    Console.WriteLine("Это функция C");
}
```

**Результат в консоли:**

```
Это функция A
Это функция B
Это функция C
Это функция A
Это функция B
Это функция C
Это функция A
Это функция B
Это функция C
```

**Пояснения:**

В основной программе функция `A()` вызывается 3 раза. Однако сама функция `A` внутри своего тела содержит вызовы функций `B()` и `C()`. Поэтому каждый отдельный вызов `A()` фактически «разворачивается» в три действия: печать текста из `A`, затем полное выполнение функции `B`, затем полное выполнение функции `C`. Так как `A()` вызвана 3 раза, весь этот блок из трёх строк повторяется трижды.

Это демонстрирует, как функции могут **группировать несколько инструкций** и как одна функция может **вызывать другие функции** внутри себя, создавая более сложную последовательность действий из простых «строительных блоков».

### 2.4 Что будет, если функцию нигде не вызвать?

**Код (добавлена функция `D`, которая нигде не вызывается):**

```csharp
A();
A();
A();

Console.ReadKey();

void A()
{
    Console.WriteLine("Это функция A");
    B();
    C();
}

void B()
{
    Console.WriteLine("Это функция B");
}

void C()
{
    Console.WriteLine("Это функция C");
}

void D()
{
    Console.WriteLine("Функция D выполнилась");
}
```

**Результат:** программа скомпилировалась и выполнилась без ошибок, но строка `"Функция D выполнилась"` **ни разу не появилась** в консоли.

**Вывод:** если функцию нигде не вызвать (ни в основной программе, ни внутри других функций), она **никогда не выполнится** — ни при запуске программы, ни в какой-либо иной момент. Определение функции — это лишь описание набора инструкций (своего рода «рецепт» или «заготовка»), которое само по себе не запускает никакого кода. Тело функции выполняется исключительно в момент явного вызова через синтаксис `ИмяФункции();`. Компилятор не считает неиспользуемую функцию ошибкой — код просто остаётся «мёртвым», невостребованным, и присутствует в файле, ничего не делая.

### 2.5 Важен ли порядок определения функций?

**Код:**

```csharp
A(); // вызываем функцию, которая внутри себя обращается к функции, определённой ниже

Console.ReadKey();

void A()
{
    Console.WriteLine("Внутри функции A");
    B(); // ссылка на функцию B, которая определена НИЖЕ в файле
}

void B()
{
    Console.WriteLine("Функция B, определена после A, но всё равно доступна");
}
```

**Результат в консоли:**

```
Внутри функции A
Функция B, определена после A, но всё равно доступна
```

Программа скомпилировалась и выполнилась **без ошибок**.

**Вывод:** порядок определения функций в файле исходного кода **не важен**. Функция, определённая раньше в тексте файла (в данном случае `A`), может свободно ссылаться и вызывать функцию, определённую позже (`B`). Это возможно, потому что компилятор C# перед началом анализа порядка выполнения сначала считывает и распознаёт **все** объявленные в файле функции целиком, а уже после этого определяет фактическую последовательность их вызовов во время выполнения программы.

Таким образом, важен только порядок **вызовов** функций (то есть в какой последовательности инструкции реально выполняются программой сверху вниз), но не порядок их **определений** (то есть места, где они физически записаны в файле).

## Общие выводы по лабораторной работе

1. Программа на C# не может быть запущена напрямую из исходного кода — обязателен этап компиляции, преобразующий текст программы в исполняемый файл.
2. Папка `obj` хранит промежуточные файлы сборки, а папка `bin` — итоговые артефакты компиляции, включая готовый `.exe`.
3. Консольное окно автоматически закрывается сразу после завершения программы; чтобы оно оставалось открытым, требуется инструкция ожидания ввода, например `Console.ReadKey()`.
4. Функции — это способ группировки нескольких инструкций под одним именем, что позволяет переиспользовать один и тот же блок кода многократно, просто вызывая функцию по имени.
5. Функция выполняется исключительно при явном вызове; неиспользуемая (невызванная) функция никогда не отрабатывает, даже если она присутствует в коде.
6. Порядок определения функций в файле не имеет значения для работы программы — важен только порядок фактических вызовов функций во время выполнения.
